# Kiln 发展路线与验收标准

> 定位、取舍与独立设计见 [LINEAGE.md](./LINEAGE.md) 与 [LICENSE-ANALYSIS.md](./LICENSE-ANALYSIS.md)。评测报告由开发仓库的 `npm run eval:fusion` 生成（生成物不入库）。

## 结论

当前版本已经能跑通一条完整的可移植应用供应链：用 `kiln cast init` 生成 Kiln 原生 cast，产出带签名的版本化 artifact，装进宿主并经过审批，再被任意 stdio / HTTP / SSE MCP agent 调用，最后可以撤销与卸载。

这条链路由开发仓库的 `npm run eval:fusion` 自动验收，12 项任务全通过。

还差两件事：在真实第三方 MCP 客户端界面里做人工验收；以及 OS 级沙箱。

更准确地说：

| 维度             | 当前状态                                                                                       |
| ---------------- | ---------------------------------------------------------------------------------------------- |
| 设计取舍         | 有清晰的独立方向：声明式应用、单文件契约、能力网关，不依赖任何外部框架                         |
| 代码与运行时复用 | 仍为 0 个外部框架/依赖引用；能力通过单文件 manifest、versioned artifact 与标准协议完成         |
| 跨客户端互操作   | cast 脚手架、宿主生命周期、HTTP/SSE MCP 均已落地；跨宿主任务链自动评测 12/12 通过              |
| 用户工作流       | 已闭环：一键包自动注册 + 宿主安装审批 + 调用 + 撤销 + 卸载；仍缺应用市场服务端与客户端人工验收 |
| 可移植性与安全   | artifact 可复现、可验签、可解包；已实现进程级隔离与审计，仍无 OS 级沙箱                        |

所以现在的成果是一条能跑的可移植供应链，不是设计原型了。但要叫「成熟平台」，还差真实客户端界面验收、应用市场服务端和 OS 级沙箱。

把外部框架的代码搬进来并不会得到 1+1>2——那只会多出一套独立的大型运行时、构建链和升级周期，也正是本项目刻意避免的。

## Kiln 的定位与边界

把「契约内核」「应用供应链」「宿主运行时」放在不同层，而不是并成一个巨型框架：

```text
Kiln cast            可移植的小应用单元（单文件 cast.json + 入口）
                      │ 经受控协议调用
Kiln 宿主            安装 / 审批 / 运行 / 撤销 / 卸载，UI 与 agent 共用 observe / act
                      │
其他 MCP clients     同一份 cast 的工具调用入口（stdio / HTTP / SSE）
```

### 借鉴并保留（通用工程经验）

- **机器可读 CLI**：稳定错误码 + 一句可执行的修复 hint + 一次检查尽量报告全部问题。
- **声明式能力授权**：应用自己说「我要什么」，宿主决定「给不给」，比运行时猜要可靠。
- **单文件产物**：一个微应用 = 一个文件 = 一个可寻址、可签名、可回滚的单位。
- **Kiln 自己的核心**：单一 manifest、`describe/invoke/observe/act`、能力申请与宿主策略求交、可解释的拒绝、紧凑示例、不依赖单一 agent 的契约。

### 不应搬入

- 不把外部框架的 DI / ORM / 支付 / 全栈构建栈塞进 Kiln 核心；Kiln 只出契约与供应链。
- 不维护第三套通用 coding-agent runtime；模型、会话、任务编排属于现有 agent 客户端。
- 不把 MCP 声明误当作安全沙箱。MCP 是互操作协议，不是隔离机制。

## 已落地的互操作纵切

`kiln mcp <cast-or-apps-dir>` 通过 stdio 提供 JSON-RPC MCP 服务。命令既可指定一个 cast，也可指定一个应用目录；扫描发现的有效 cast 会合并为单个 MCP 工具集。Studio 和 MCP 共用同一目录发现逻辑。

- `tools/list` 暴露 `describe`、`invoke`，以及 cast 声明的 `observe` / `act` 能力。
- `tools/call` 仍由 Kiln `CastRunner` 执行，所以宿主策略、能力网关和拒绝记账仍然生效。
- stdio `stdout` 只写 MCP 消息；启动错误与诊断写 `stderr`。
- 工具名明确区分动词：`<castId>__describe`、`<castId>__invoke__<tool>`、`<castId>__observe`、`<castId>__act__<action>`。
- 重复 cast ID 会被拒绝；目录中无法加载的 cast 会输出诊断，其他有效 cast 仍可使用。

这条接缝同时适合任意标准 MCP 客户端，不需要 Kiln 依赖任何外部框架。直接使用 `kiln mcp` 时仍需在客户端手动注册；`kiln up` 已能自动探测并合并写入该配置（见 [ONE.md](./ONE.md)）。**目前验证的是 Kiln 的 MCP 协议回归测试与 Kiln One 的真实 stdio 自检，不代表已经在真实第三方客户端的 UI/运行时里完成端到端验收。**

## 分阶段路线

| 阶段                                     | 目标                                                                               | 验收条件                                                                                                                  |
| ---------------------------------------- | ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| P0：协议接缝（已落地）                   | MCP stdio 服务覆盖四动词、支持应用目录并复用 runner 授权路径                       | JSON-RPC 握手、多个 cast 发现与路由、task 调用、panel observe/act 自动化测试通过；stdout 无非协议内容                     |
| P1：普通用户首个闭环（已落地，本仓库内） | 选定高频痛点「日常信息收纳与再找到」，交付自描述一键包、自动连接、可读权限与撤销   | 已通过：`one/` 一键包 + `kiln up` 自动注册与真实握手自检 + 授权撤销 + 96 个自动化测试；仍缺应用商店与客户端 UI 端到端评测 |
| P2：artifact 稳定性（已落地）            | 规范化摘要、逐文件哈希、兼容声明、可复现构建、Ed25519 签名与安全解包               | 同一目录两次构建摘要一致；篡改与错误公钥均被拒；`test/fusion.spec.ts` 覆盖                                                |
| P3：原生 cast 脚手架（已落地）           | `kiln cast init` 生成、`kiln cast check` 校验原生 cast，零外部依赖                 | `kiln cast init/check` 生成并校验通过，不引入任何外部框架依赖                                                             |
| P4：宿主生命周期（已落地）               | 安装 / 更新 / 审批 / 撤销 / 运行 / 面板 / 卸载，UI 与 agent 共用 `observe` / `act` | 默认安装即未授权，审批后可调用、撤销后立即拒绝，全流程写审计并自动验收                                                    |
| P5：安全发布与运行隔离（部分落地）       | Ed25519 签名、JSONL 审计、子进程隔离、超时与环境变量白名单、可选 Node 权限模型     | 进程级隔离已验收（子进程 pid 不同于宿主）；**OS / 容器级隔离仍缺，不可信代码仍需外部沙箱**                                |
| P6：真实产品评测（已落地，本地模拟宿主） | 跨宿主 12 项任务链评测、HTTP/SSE MCP、发现层、多租户                               | 开发仓库 `npm run eval:fusion` 12/12 通过并可生成评测报告（生成物不入库）；真实客户端界面人工验收仍未完成                          |

实际落地顺序为**普通用户闭环 → artifact 与签名 → 进程隔离/审计 → 脚手架与宿主生命周期 → 跨宿主评测**。P2/P3/P4/P6 已通过自动验收；P5 的进程级部分已落地，OS 级沙箱仍是开放项。在真实客户端界面完成人工验收前不宣称「原生集成」；在 OS 级隔离完成前不宣称可安全运行第三方 cast。

## 安全与许可边界

stdio MCP 服务仍在当前 Node 进程中 import 并运行 cast。`--policy strict` 能收紧经 `ctx.cap` 的能力，但不能阻止 cast 代码直接导入 Node API。只对自己编写或审核过的 cast 使用；不要把本地 MCP 服务作为不可信代码的沙箱。

Kiln 当前为 Apache-2.0。本项目只做协议互操作与原创实现，不复制任何外部项目的实现；若后续确需复用第三方代码，必须逐文件核对版权、依赖与 NOTICE，而不能仅凭对方主许可证推断。
