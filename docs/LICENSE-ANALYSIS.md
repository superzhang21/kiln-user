# 许可分析与合规结论

> 这里是工程判断，不是法律意见。涉及实际商业发行前，请让律师过一遍。

## 1. 采用的许可

Kiln 采用 **Apache-2.0**（`LICENSE` 为全文，`package.json` 已声明 `"license": "Apache-2.0"`）。本文说明选择理由与边界。

## 2. 为什么是 Apache-2.0（而非更宽松的 MIT）

| 考量       | MIT    | Apache-2.0                        | 对本项目的意义                         |
| ---------- | ------ | --------------------------------- | -------------------------------------- |
| 专利授权   | 无     | §3 明示授予，且含专利诉讼反击条款 | 平台类项目要面对企业法务，这条是硬门槛 |
| 商标       | 未提及 | §6 明确「不授予商标权」           | 反向保护：别人 fork 后不能挂你的名字   |
| 致谢机制   | 无     | `NOTICE` 文件 + §4(d) 传递义务    | 需要给第三方致谢时有正式位置           |
| 修改标注   | 无     | §4(b) 要求修改过的文件显著标注    | 对「衍生再造」反而有利：血缘显式化     |
| 贡献者条款 | 无     | §5 默认贡献即同许可               | 多人协作时减少扯皮                     |

一句话：**MIT 让人用得方便，Apache-2.0 让人用得放心。** 这个项目要给别人当底座，选后者。

### 2.1 兼容性方向（单向，别搞反）

```
MIT → Apache-2.0：兼容。
Apache-2.0 → MIT：不兼容。
```

- **MIT → Apache-2.0 可行**：MIT 只要求保留声明，Apache-2.0 能完整满足且附加更多保护。
- **Apache-2.0 → MIT 不可行**：MIT 承载不了 Apache-2.0 的专利与 NOTICE 义务，会造成许可冲突。

### 2.2 一个现实约束

Apache-2.0 → MIT 不通，意味着「把 Kiln 的代码以 MIT 形式回馈给要求 MIT 的项目」在许可上走不通。

若将来出现下游要求 MIT 兼容，有三条路：

1. **本项目改回 MIT**，另附一份 `PATENTS` 文件做独立专利不主张声明。代价是专利保护弱于 Apache-2.0，且没有正式的商标条款。
2. **双许可**：`MIT OR Apache-2.0`，让下游自选。这是 Rust 生态的通行做法，成本最低。
3. **保持 Apache-2.0**，接受单向消费。若项目定位是「独立平台」，这是合理的。

**当前决定：走第 3 条。** 理由是这个项目要给别人当底座，专利授权与商标条款比回馈某些下游更要紧；而「回馈」目前没有真实需求，为一个假设的需求牺牲专利保护不划算。

**改判条件**：出现「下游明确要求 MIT 兼容」这类具体情况时，再切第 2 条。切换动作是**一次提交**：`package.json` 改 `"MIT OR Apache-2.0"` + 补 `LICENSE-MIT` + 更新 `NOTICE` 与 README 的许可段。不需要提前留口子。

**这一条只写在本文档里。** README 的许可段不承担决策说明（见 §4）。

## 3. 独立实现与第三方边界

本项目为独立实现：内核分层、四动词契约、单文件 `cast.json`、能力网关与宿主策略求交、可解释拒绝、强制示例——均基于 Node 内置 API 写成，不复制任何外部项目的代码或文档原文。

若将来确需引入第三方组件，按 `NOTICE` 的登记政策逐项正确标注其许可与版权；`NOTICE` 的机制（§4(d) 传递义务）正是为此准备。

## 4. 各文件的分工

| 文件           | 该写什么                           | 不该写什么                           |
| -------------- | ---------------------------------- | ------------------------------------ |
| `LICENSE`      | 许可全文                           | 任何解释                             |
| `NOTICE`       | 第三方材料的范围、追加政策         | 对未来的承诺、绝对化的自我认定       |
| `README`       | 一句「什么许可 + 指向 NOTICE」     | 法律声明、其他项目名、维护者操作指引 |
| `CONTRIBUTING` | 贡献必须是原创、第三方材料如何登记 | 许可选择理由                         |
| 本文档         | 决策过程与兼容性推理               | ——                                   |

**README 的许可段就是两句话。** 读者在那里只想知道两件事：什么许可、我要承担什么义务。

同理，`NOTICE` 里不要写「本项目未复制任何代码」这种绝对化陈述。它对未来不成立（任何人一次提交就能推翻），而且无法持续验证。改成**对当前内容的范围描述 + 对后续追加的政策**，这两条都是可维护的。
