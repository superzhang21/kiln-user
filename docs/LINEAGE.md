# 设计取舍与差异

这份文档回答两个问题：**Kiln 自己做了哪些关键取舍**，以及**凭什么说它不是对某个现有框架的改名**。

## 一、核心设计对照

| 维度         | Kiln 的做法                                                                       |
| ------------ | --------------------------------------------------------------------------------- |
| 单元叫法     | **cast**（一个文件夹，单文件 `cast.json` + 入口）                                 |
| 对外契约     | **四动词 pact**：`describe` / `invoke` / `observe` / `act`                        |
| 能力访问     | **`CapabilityGateway` 单一出口**                                                  |
| 授权模型     | **清单申请 × 宿主上限求交，裁剪可查**                                             |
| 错误形态     | **`KilnError` + 一次返回全部问题（含 `code`/`hint`/`docs`）**                     |
| 扩展机制     | **`PluginApi` 四个 `add*`**                                                       |
| 目录结构     | **`grain` / `forge` / `pact` / `host` / `surface` 五层**（另有 `studio` / `one`） |
| 构建产物     | **契约产物（不打包）**                                                            |
| agent 运行时 | **不自带，只出契约**                                                              |

## 二、采纳的通用工程经验

这些不是从某个项目抄来的，而是被广泛验证、被本项目独立采用的实践：

| 采纳                                                           | 为什么值得采纳                                               |
| -------------------------------------------------------------- | ------------------------------------------------------------ |
| **错误即接口**：稳定 code + 一句可执行的 hint + 固定 docs 链接 | 省 token 性价比最高的一条。一次重试的代价远超一条好 hint     |
| **一次报全部问题**                                             | 面向 agent 优化：修一个跑一次是双重浪费                      |
| **结构化输出 + 稳定 schema**                                   | `--json` 单条结果、`schemaVersion`、退出码 0/1/2 分明        |
| **声明式能力授权**                                             | 应用自己说「我要什么」，宿主决定「给不给」，比运行时猜要可靠 |
| **单文件产物**                                                 | 一个微应用 = 一个文件 = 一个可寻址、可签名、可回滚的单位     |
| **市场作为分发面**                                             | 承认分发是平台的一部分（本项目尚未实现）                     |

## 三、明确拒绝的设计

拒绝比采纳更能说明这不是复制。

| 拒绝什么                                  | 理由                                                                                              |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------- |
| 双文件清单（`xxx.yml` + `xxx.config.ts`） | 一个 cast 该只有一份声明。两个文件意味着两处可能不一致，而 agent 最怕不一致                       |
| DI 容器 + 装饰器 + 反射元数据             | 为大型长生命周期应用设计，代价是产物要带元数据、tree-shaking 失效。微应用只需要**启动快、体积小** |
| ORM / 声明式事务 / OAuth2 / 支付全家桶    | 企业级骨架。微应用多数场景用不上，却要为它付依赖成本                                              |
| 内置打包与多种部署器                      | 绑死运行形态。这里先只出契约，等真需要时再为具体的谁打                                            |
| 自建 agent 运行时                         | **重复投资**。跟成熟 agent 客户端正面竞争，且没有分发优势                                         |
| 把前端内嵌进后端                          | 有状态的服务端应用不该同时是 UI 包。两种消费者该有两条产物                                        |
| 多层 Harness 抽象                         | 对「微应用平台」是多余的抽象层。会话策略是 agent 客户端的事，不是契约层的事                       |
| 桌面宿主 / Tauri / Rust 运行时            | 本项目不做客户端。宿主应该是可嵌入的库，不是一个应用                                              |
| 把「声明」当「授权结论」                  | 声明只是申请。**申请和批准是两件事**，必须求交，且要能解释为什么拒                                |
| 全局命名空间                              | 全局对象难类型化、难 tree-shake、多个 cast 同页会打架。改用注入的 `ctx.cap`，作用域天然收敛       |
| 把自有 agent 会话塞进微应用               | 职责混淆。需要模型能力就用 `model` 这一档能力表达，不要在小应用里开一个隐形的 agent               |
| iframe 承载                               | 是合理的隔离手段，但只是**渲染层**隔离，不解决授权。本项目先把授权做对，渲染层留空                |

## 四、Kiln 独有的

这些在常见的微应用框架里都找不到对应物：

1. **拒绝记账（不可被吞）**。业务错误允许 cast 吞掉，越权不允许——网关在拒绝时另记一笔，执行器在动词返回后用它覆盖返回值。机制见 [ARCHITECTURE.md](./ARCHITECTURE.md#1-拒绝不可被吞)。
2. **双向求交的授权**。清单申请 × 宿主上限，取交集；超出部分被裁掉但**记录在案**（`dropped`），不静默放行、也不整体拒绝。
3. **强制示例**。每个工具必须有真实的 `call` + `result`，校验器硬性拦截。理由是 token 账，不是洁癖。
4. **适配器 weight**。每个适配器声明体积系数，让调度器能在「结构精确」与「文字省」之间做显式取舍，而不是拍脑袋。
5. **单一清单文件**。一个 cast 只有一份可信声明。
6. **构建不打包**。只产出契约，把运行形态的决定权推后。

## 五、独立性自查

这几条是可验证的，不是自我声明：

- 内核五层（`grain` / `forge` / `pact` / `host` / `surface`）的划分与职责边界在常见框架里都不存在；此外还有 `studio` 与 `one` 两个包，分别承担本机界面与产品层。
- 四动词语义无对应物。注解式 Controller 或 `window.app.*` 加 `expose()` 这类方案，没有把 `describe` / `invoke` 做成一套可选组合的契约。
- 没有任何文件是从外部项目复制后改名的。所有实现基于 Node 内置 API 写成。
- 没有引用任何外部项目文档原文。本仓库 `docs/` 下的中文表述均为本项目自撰。
- 未使用任何第三方商标、logo、产品名。见 `NOTICE`。

## 六、接缝设计原则

明确记录在此，避免以后重走弯路：

**不要合并 agent 运行时。** 多个通用 agent 运行时各自存在，再做一个就是第三份重复投资。Kiln 的定位是**只出契约**，让任何运行时来接。

**接缝是 versioned artifact / manifest 与标准协议（MCP stdio 等），不是共享代码库。** 静态清单与打包产物用于校验、分发和审阅；运行中的 cast 通过标准协议交给宿主调用。共享实现会绑死两边的演进节奏，而这个领域半年换一代。

当前已经有 Kiln 的 MCP stdio 服务，这是通用互操作层。可信发布与宿主生命周期见 [INTEGRATION-PLAN.md](./INTEGRATION-PLAN.md)（发展路线）。
